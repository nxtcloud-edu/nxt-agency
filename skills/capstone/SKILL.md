# ⚡ 캡스톤 프로젝트

아이디어만 있는 캡스톤·졸업작품을 발표 가능한 상태까지 끌고 갑니다. 먼저 범위를 줄여 꼭 필요한 기능만 고르고, 며칠 안에 돌아가는 시제품(MVP, 최소 기능 제품)을 만들고, 서버 구조와 화면을 정리한 뒤, 심사 전에 코드 리뷰와 발표 자료를 준비합니다. 팀 프로젝트로 웹앱·서비스를 만드는 학부생·대학원생용입니다. 완벽한 설계보다 "일단 돌아가는 것"에서 배우는 순서를 따릅니다.

## 시작할 때 물어볼 것
1. 무엇을 만들고 누가 쓰는 서비스인가요? 한 문장으로 말해 주세요. (기본값: 한 문장이 나오기 전까지 진행하지 않음)
2. 다음 발표·제출 마감은 언제이고 팀원은 몇 명인가요? (기본값: 마감 2주, 팀원 3명으로 가정하고 계획에 명시)
3. 쓰기로 정한 언어·프레임워크가 있나요? (기본값: 팀이 이미 아는 것을 우선하고, 없으면 Next.js + Supabase + Vercel)

각 단계가 끝날 때 "여기까지 확인하시겠어요?"라고 한 번만 묻고, 사용자가 "계속"이라고 하면 이후 단계는 멈추지 않고 진행합니다.

## 진행 단계

### 1단계. 범위 축소·최소 기능 정의 — 전문가: `rapid-prototyper`(빠른 시제품 개발자)
- **위임**: `rapid-prototyper` 서브에이전트가 설치되어 있으면 그에게 맡긴다. 없으면 아래 요령으로 직접 한다.
- **요령**:
  - 검증할 핵심 가설을 한 문장으로 적는다. "○○한 사용자는 △△ 기능을 쓸 것이다."
  - 핵심 사용자 흐름(처음부터 끝까지 한 번 쓰는 여정) 하나를 정하고, 그 흐름에 필요한 최소 기능 3~5개만 고른다. 나머지는 전부 "나중에" 목록으로 보낸다.
  - 만들기 전에 성공·실패 기준을 정한다. "시연 때 사용자 5명 중 4명이 핵심 흐름을 끝까지 완료" 같은 식으로.
  - 개인정보(학번·이메일)는 최소한만 받고 수집 목적을 안내하도록 처음부터 정한다.
  - 마감까지 남은 날짜를 일 단위로 쪼개 무엇을 언제 끝낼지 정한다. 발표 전날이 아니라 발표 3일 전에 돌아가는 것이 목표다.
- **이 단계 산출물**: 시제품 개요

  ```markdown
  ## 🧪 시제품 개요
  **핵심 가설**: [어떤 사용자의 어떤 문제를 해결하는가?]
  **성공 지표**: [검증 성공을 어떻게 측정하는가?]
  **핵심 흐름**: [처음부터 끝까지 필수 사용자 여정]
  **기능 목록**: [초기 검증용 최대 3~5개]
  **나중에 목록**: [이번 발표에서 뺀 기능]
  **일정**: [D-day 기준 날짜별 목표]
  ```

- **다음 단계로 넘길 것**: 핵심 흐름, 기능 목록 3~5개, 스택 결정, 마감 일정

### 2단계. 동작하는 시제품 — 전문가: `rapid-prototyper`(빠른 시제품 개발자)
- **위임**: `rapid-prototyper` 서브에이전트가 설치되어 있으면 그에게 맡긴다. 없으면 아래 요령으로 직접 한다.
- **요령**:
  - 설정 시간이 가장 짧은 도구를 고른다. 로그인은 Clerk 같은 서비스나 학교 구글 계정 로그인, 데이터베이스는 Supabase·Firebase 같은 BaaS(서버를 대신 운영해 주는 서비스), 화면은 shadcn/ui 같은 기존 컴포넌트를 쓴다.
  - 첫날에 배포부터 한다. Vercel 등에 올려 팀원·지도교수가 바로 열어 볼 수 있는 URL을 만든다.
  - 핵심 기능 먼저, 다듬기와 예외 처리는 나중에. 인프라·최적화보다 사용자 눈에 보이는 기능에 집중한다.
  - 첫날부터 피드백 폼과 간단한 이벤트 추적을 넣는다. 발표 때 "사용자 N명이 써 봤고 이런 의견이 있었다"고 말할 수 있어야 한다.
  - 기능을 쉽게 붙이고 뗄 수 있게 모듈 구조로 만들어 피드백에 따라 빠르게 고친다.
  - 같은 과 학생·수업 수강생·지도교수와 테스트 일정을 잡고, 성공 지표를 매일 확인한다.
- **이 단계 산출물**: 배포된 시제품 URL + 시제품 보고서

  ```markdown
  # [프로젝트명] 시제품 보고서
  ## ⚙️ 기술 구현
  **스택**: [예: Next.js + TypeScript + Tailwind / Supabase + Prisma / Vercel]
  **구현 기능**: [로그인, 핵심 기능, 피드백 폼, 이벤트 추적]
  **배포 URL**: [ ]
  ## ✅ 검증 체계
  **피드백 수집**: [테스트 일정, 앱 내 피드백 폼]
  **반복 계획**: [매일 확인할 지표, 방향 전환 기준]
  ```

- **다음 단계로 넘길 것**: 저장소, 배포 URL, 사용자 피드백, 발표 전에 정리해야 할 문제 목록

### 3단계. 구조·화면 정리 — 전문가: `backend-architect`(백엔드 설계자), `frontend-developer`(프론트엔드 개발자)
- **위임**: `backend-architect`와 `frontend-developer` 서브에이전트가 설치되어 있으면 서버와 화면을 각각 맡긴다. 없으면 아래 요령으로 직접 한다.
- **요령(서버)**:
  - 예상 사용자 수, 데이터 규모, 팀 규모, 개인정보 포함 여부를 확인한 뒤 현재 부하를 만족하는 가장 단순한 구조를 고른다. 학생 팀 프로젝트는 대개 모듈형 모놀리스(한 서버 안에서 기능별로 폴더를 나눈 구조)가 정답이다. 마이크로서비스는 쓰지 않는다.
  - 데이터 모델과 API 계약(어떤 주소로 무엇을 보내면 무엇이 오는지)을 OpenAPI 명세 같은 문서로 코드보다 먼저 적는다. 오류 응답 형식을 통일한다.
  - 비밀번호는 bcrypt 등으로 해시해 저장하고, 학번·연락처 같은 개인정보는 최소 수집·암호화 저장·보유 기간 명시를 지킨다(개인정보보호법).
  - 외부 호출에는 타임아웃과 재시도를 두고, 요청 ID가 담긴 구조화 로그를 남긴다.
- **요령(화면)**:
  - 모바일 우선 반응형으로 만든다. 심사위원이 휴대폰으로 열어 봐도 깨지지 않아야 한다.
  - 시맨틱 HTML과 ARIA 레이블을 쓰고 키보드로 모든 기능이 조작되게 한다. 대학·공공기관 서비스는 웹 접근성(KWCAG) 준수 의무가 있다.
  - 한글 입력은 `compositionend` 이벤트를 함께 처리하고, 한글 웹폰트는 서브셋과 `font-display: swap`을 적용하고, 날짜·숫자는 `ko-KR` 로캘로 표시한다.
  - 크롬·엣지·사파리·삼성 인터넷에서 핵심 흐름을 한 번씩 확인한다. Lighthouse 성능·접근성 90점을 목표로 한다.
- **이 단계 산출물**: 시스템 구조 명세서 + 프론트엔드 구현 보고서

  ```markdown
  # 시스템 구조 명세서
  **구조 패턴**: [모듈형 모놀리스 등] / **통신 패턴**: [REST/GraphQL]
  **데이터 모델**: [핵심 테이블과 관계, 개인정보 컬럼 표시]
  **API 계약**: [엔드포인트 목록, 오류 응답 형식]
  **보안**: [인증 방식, 암호화, 개인정보 보유 기간]

  # 프론트엔드 구현 보고서
  **프레임워크·스타일링**: [ ] / **상태 관리**: [ ]
  **접근성**: [KWCAG 점검 결과, 키보드 탐색, 스크린 리더]
  **성능**: [Lighthouse 점수, 브라우저 확인 결과]
  ```

- **다음 단계로 넘길 것**: 정리된 저장소, 구조 명세서, 남은 기술 부채 목록

### 4단계. 코드 리뷰·발표 준비 — 전문가: `code-reviewer`(코드 리뷰어)
- **위임**: `code-reviewer` 서브에이전트가 설치되어 있으면 그에게 맡긴다. 없으면 아래 요령으로 직접 한다.
- **요령**:
  - 정확성 → 보안 → 유지보수성 → 성능 → 테스트 순서로 본다. 취향 논쟁(탭·스페이스)은 하지 않는다.
  - 의견마다 🔴 차단 / 🟡 제안 / 💭 사소를 붙인다. 🔴는 심사 전에 반드시 고치고, 🟡은 시간이 있으면, 💭는 발표 후로 미룬다.
  - 하드코딩된 API 키·비밀번호·토큰은 항상 🔴다. 환경변수로 옮기고 키를 재발급한다. GitHub에 공개하기 전에 커밋 이력에도 남아 있지 않은지 확인한다.
  - "보안 문제"가 아니라 "42번째 줄에서 SQL 인젝션이 발생할 수 있습니다"처럼 구체적으로 쓰고, 왜 그런지 이유를 붙인다. 잘한 부분도 짚어 준다.
  - 리뷰는 한 번에 완전하게. 여러 라운드에 걸쳐 조금씩 흘리지 않는다.
  - 발표 준비: 시연 순서를 핵심 흐름 그대로 짜고, 시연이 실패할 때 보여 줄 녹화 영상이나 스크린샷을 준비한다. 심사 예상 질문("왜 이 기술을 썼나", "사용자가 정말 필요로 하나", "확장하면 어디가 먼저 막히나")에 대한 답을 시제품 보고서와 구조 명세서에서 뽑는다.
- **이 단계 산출물**: 리뷰 요약 + 발표 준비표

  ```markdown
  ## 리뷰 요약
  **전체 인상**: [한두 문장]
  **잘한 점**: [구체적으로]
  **핵심 우려**: [🔴 차단 항목 요약]
  ## 다음 단계
  - [ ] 🔴 항목 수정 후 재확인
  - [ ] 🟡 항목은 발표 전 또는 후속 이슈로

  ## 발표 준비표
  | 순서 | 보여 줄 것 | 말할 것(한 문장) | 실패 시 대안 |
  | --- | --- | --- | --- |
  **예상 질문과 답**: [3~5개]
  ```

- **다음 단계로 넘길 것**: 없음(최종 산출물로 전달)

## 최종 산출물
- 시제품 개요(핵심 가설, 기능 3~5개, 나중에 목록, 일정)
- 배포된 시제품 URL과 시제품 보고서
- 시스템 구조 명세서와 프론트엔드 구현 보고서
- 코드 리뷰 요약(🔴🟡💭)과 발표 준비표, 예상 질문 답
- 파일로 필요하면 저장소의 `docs/` 폴더에 마크다운으로 저장하고, 발표 자료는 발표 준비표를 슬라이드 순서로 옮긴다.

## 하지 말 것
- 없는 사실·수치·법령 조항 번호를 지어내지 않는다. (공통)
- 개인정보(이름·학번·연락처)를 예시나 결과에 넣지 않는다. (공통)
- 1단계에서 정한 기능 3~5개 밖의 기능을 발표 전에 추가하지 않는다. 새 아이디어는 "나중에" 목록으로 보낸다.
- 학생 팀 프로젝트에 마이크로서비스, Kubernetes 같은 운영 복잡도가 큰 구조를 권하지 않는다.
- API 키·비밀번호를 코드나 커밋 이력에 남긴 채 저장소를 공개하지 않는다.
